### Validação profunda do dataset Kaggle (inspeção direta do CSV real, além da descrição pública)
Fui além da checklist inicial da Fase 1 e inspecionei o `generate_dataset.py` (script gerador, 1898 linhas) e os CSVs reais do mirror público no GitHub (`mominullptr/FIFA-World-Cup-2026-Dataset`), já que baixar via API do Kaggle exigiria credenciais ainda não configuradas neste ambiente.

- **Confirmado: dado real, não sintético.** O script cita fonte por partida (`fifa.com`/`sofascore.com`) e tem um sistema elaborado de correção manual de nomes de jogador pra bater assistência/gol com o `player_id` certo — não é um simulador de torneio. A única parte de fato aleatória é uma estimativa de `market_value_eur` (com seed reprodutível por `player_id`) usada só quando não há valor real conhecido pro jogador — não afeta nenhum dos módulos planejados.
- **Achado importante sobre staleness**: o `generate_dataset.py` do mirror do GitHub está congelado a partir da partida 93 (rodada de 16, 6 de julho) — é só o script de bootstrap inicial. As atualizações reais (incluindo a final) são aplicadas diretamente nos CSVs por scripts pequenos e dedicados (`update_m103.py`, `update_m104.py`, committados 2026-07-18/2026-07-20). **Conclusão prática: sempre puxar os CSVs diretamente (ou via API do Kaggle), nunca depender do script gerador pra saber o estado atual do dataset.**
- **O torneio já está 100% completo no dataset**: `matches.csv` tem as 104 partidas com `status = Completed`. A final (`match_id 104`) confirma exatamente a narrativa do projeto: Espanha 1x0 Argentina, `result_type = AET`, gol aos 106min. `match_team_stats.csv` da final: Espanha 65% posse / 20 finalizações / 12 no alvo vs. Argentina 35% posse / 2 finalizações / 0 no alvo — bate com a leitura "domínio esmagador sem prêmio proporcional" do Módulo C quase à risca. O terceiro lugar (`match_id 103`) confirma o 6x4 do Módulo F.
- **Granularidade real confirmada**: `match_events.csv` é gol/cartão/VAR com minuto exato (ex: os dois cartões vermelhos da Argentina na final, aos 93min e 120min), **não é uma finalização registrada por evento** — pra volume de finalizações minuto a minuto (se algum módulo precisar disso no detalhe), só dá pra usar o agregado por partida de `match_team_stats`, não um replay evento a evento.
- **Checagem de integridade referencial** rodada contra os CSVs reais (script em `python`/pandas, não versionado — validação pontual): zero violações de FK em `matches`/`match_events`/`match_team_stats`/`match_lineups`/`squads_and_players`, zero duplicatas de PK, zero partida com `home_team_id = away_team_id`, zero nulos nas colunas obrigatórias de `matches`. Schema em `sql/schema.sql` já reflete essa estrutura validada.

### Decisões de design do schema
- `match_prediction_features.csv` (65 features de ML) e `matches_detailed.csv` (join denormalizado) **não viraram tabelas**: o primeiro não serve ao objetivo do projeto (testar teses, não prever resultado); o segundo foi recriado como `VIEW` (`matches_detailed`) pra não guardar uma cópia denormalizada que pode dessincronizar das tabelas-base.
- `player_stats.csv` foi normalizado: as colunas `player_name`/`team_id`/`position`, redundantes com `players`, foram descartadas da tabela — acessíveis via `JOIN` por `player_id`.
- `historical_champions` é uma tabela nova, sem equivalente no dataset Kaggle (que só cobre 2026) — existe especificamente pra alimentar o Módulo A com dado histórico via Wikipedia, com `goals_conceded_per_game` como coluna gerada (`GENERATED ALWAYS AS ... STORED`).

### Validação de fontes (perguntas em aberto da Fase 1, `project-scope.md` seção 8)
- **Dataset Kaggle `mominullptr/fifa-world-cup-2026-dataset`**: confirmado relacional, 12 tabelas (`teams`, `venues`, `tournament_stages`, `referees`, `matches`, `matches_detailed`, `squads_and_players`, `match_events`, `match_team_stats`, `match_lineups`, `player_stats`, `match_prediction_features`). `match_events.csv` é evento-a-evento com minuto (gols, assistências, cartões, VAR); `match_team_stats.csv` traz estatísticas agregadas por time por partida (posse, finalizações, escanteios, faltas, impedimentos, defesas), não evento-a-evento de finalização. **Cobre só a Copa 2026** — nenhum dado histórico de Copas anteriores. Isso confirma que o Módulo A (comparação histórica de gols sofridos por campeão) depende de Wikipedia/outra fonte, não deste dataset; e que o Módulo C (finalizações/xG minuto a minuto na final) provavelmente vai precisar trabalhar com os totais agregados de `match_team_stats` em vez de um evento por finalização — a granularidade exata só será confirmada ao inspecionar o CSV real (a descrição pública pode não ser exaustiva).
- **football-data.org**: World Cup está no tier grátis (10 chamadas/min, 12 competições), mas **dado histórico no free tier fica limitado à temporada atual** — não cobre Copas passadas. Decisão: não serve como fonte primária do Módulo A; Wikipedia (ou outro dataset histórico dedicado) vira a fonte principal para gols sofridos por campeão em Copas anteriores, com football-data.org restrito a validação cruzada de dados da própria Copa 2026.
- **Squawka**: sem API pública — a própria Squawka já respondeu publicamente que uma API encontrada era "interna e não deveria ser pública". Acesso estruturado via Opta/StatsPerform seria só via contrato comercial direto. **Decisão preliminar: Módulo G (pressing/PPDA) não é viável via Squawka.** Como o próprio escopo já tratava isso como stretch goal descartável, o projeto segue sem ele; se um substituto (ex: métricas de pressão já presentes no StatsBomb Open Data pro recorte de 2022) fizer sentido, é uma decisão a discutir separadamente, não um scraping da Squawka.
